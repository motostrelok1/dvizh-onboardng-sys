# LMS

## Автоматические проверки (CI)

GitHub Actions запускает `.github/workflows/ci.yml` для каждого PR, при
обновлении `main` и вручную через **Actions → CI → Run workflow**.
Используется Node.js 24 (версия зафиксирована в `.nvmrc`) и установка
из корневого `package-lock.json` через `npm ci`.

Две проверки работают независимо:

- **Server and client build** — TypeScript сервера и клиента, Vite и PWA.
- **PostgreSQL and auth tests** — отдельная PostgreSQL 16, все миграции,
  повторный запуск миграций и 157 тестов: авторизация, rate limits, CSRF,
  runtime-валидация и безопасные ошибки, дедлайны и доступ к тестам,
  health, вложения, файловое хранилище и содержимое файлов.

Тесты проверяют 401/403, роли, вход/выход, истечение сессии, блокировку
существующей сессии после отключения сотрудника (SEC-01), Secure-cookie
в production (SEC-02), одноразовые/отозванные/просроченные приглашения и
изоляцию назначенного курса между пользователями, лимиты входа/приглашений,
параллельные запросы авторизации и безопасное определение IP. Они используют настоящие
маршруты и SQL. Рабочая БД и production-секреты для CI не нужны.
Целостность вопросов/вариантов и гонки учебных попыток (DEV-01), а также
тесты интерфейса — следующие задачи; этот набор пока не покрывает все функции LMS.

Локальная сборка (из корня репозитория):

```bash
npm ci
npm run build
```

Локальные интеграционные тесты требуют отдельную локальную PostgreSQL с
базой `lms_test`. Создайте её отдельно от рабочей базы; подставьте своего
пользователя и URL-кодированный пароль в следующую команду:

```bash
export TEST_DATABASE_URL='postgres://TEST_USER:URL_ENCODED_PASSWORD@127.0.0.1:5432/lms_test'
DATABASE_URL="$TEST_DATABASE_URL" npm run migrate --workspace server
npm test
```

`npm test` не читает `.env`, не использует рабочую `DATABASE_URL` и
отказывается запускаться без `TEST_DATABASE_URL`, локального адреса и
имени базы с окончанием `_test`. Тестовые данные имеют случайные UUID;
очистка удаляет только собственные записи, без `TRUNCATE`.

Перед слиянием PR откройте **Checks** и дождитесь успеха обеих проверок.
CI сам не сливает PR и не развёртывает приложение. Для обязательного
запрета слияния при ошибке проверки отдельно настройте защиту `main` с
этими двумя проверками; один workflow не включает защиту ветки.

## Проверка входных данных и безопасные ошибки (SEC-11)

JSON Schema применяется к body/params/query маршрутов `auth`, `admin-users`,
`admin-tests`, `admin-attachments`, перечисленных в SEC-11. Ajv не приводит
типы, не подставляет значения и не удаляет неизвестные поля: неверный тип,
UUID, неизвестный параметр или лишнее поле дают 400 `invalid_request`.
Неверный lessonId при загрузке сохраняет 400 `invalid_lesson_id`.
Схемы отклоняют запросы до бизнес-обработчиков, изменения пользователей/
учебных данных и записи файлов. Auth onRequest IP counters расходуются
ещё раньше. Проверка схем происходит до preHandler авторизации;
правильный ввод всё равно требует нужной роли.

Ограничения нового ввода: ФИО до 256 символов, email до 254 с проверкой
формата, действующий часовой пояс IANA до 100; текст вопроса/варианта —
непустой, не только пробелы, до 10 000 символов, без NUL. Проходной балл —
целое 0…100; maxAttempts — целое 1…2 147 483 647 или `null` (безлимит).
boolean принимается только как JSON boolean; пустой PATCH не принимается.
Это не мигрирует и не исправляет старые данные.

Авторизация сохраняет onRequest IP limits, бюджет токена/пользователя,
минимум 8 символов и максимум 72 UTF-8 байта нового пароля после счётчиков.
Схема ограничивает строку пароля до 1024 символов, body до 8 КиБ; вход
с bounded legacy-паролями и email сохраняется. Неизвестные поля отклоняются.
Настройки счётчиков и cookie из SEC-06/08 сохраняются.

Response DTO перечисляют поля ответов этих модулей. Пароли/хеши, будущие
внутренние столбцы и `file_path` вложения не сериализуются; клиент получает
id и метаданные файла. Бинарное скачивание сохраняет проверку доступа,
фиксированный Content-Type, Content-Disposition и nosniff.

Общий error handler подключён в корневом index.ts и в этих модулях.
Ошибки схемы/JSON — 400 `invalid_request`, слишком большой body — 413
`payload_too_large`, неизвестный media type — 415 `unsupported_media_type`.
Не-multipart загрузка сохраняет 406 с безопасным кодом; ошибка грамматики
multipart — 400 без parser details. Ошибки FK — 409 `invalid_reference`,
неперехваченный unique conflict — 409 `conflict`; неожиданные исключения —
500 `internal_error`. SQL, detail/message, stack и внутренние пути не
возвращаются клиенту. Для неожиданных ошибок пишутся фиксированная категория
и request id, без текста исключения. Domain-ответы обработчиков (например,
email_taken, invitation_used, rate_limited/Retry-After) сохраняют свой контракт.

Добавлены 7 проверок без БД и 11 PostgreSQL/API-сценариев: типы/границы,
ошибки парсера, DTO, отсутствие изменений при отказе и обычный CRUD.
Проверки хранения читают file_path напрямую из своих fixture-записей БД.
Ajv 8.20.0 и ajv-formats 2.1.1 закреплены как прямые зависимости; это уже
использовавшиеся версии в lockfile. Новой миграции нет; обычное обновление
через npm ci, сборку и restart всех серверных экземпляров. VDS не менялся.

Целостность и гонки учебных попыток (DEV-01) и схемы остальных
API-модулей — отдельные задачи. SEC-11 охватывает указанные выше
четыре модуля.

## Частичные обновления сотрудника и теста (H13 / DEV-06)

В `PATCH /admin/users/:id` и `PATCH /admin/tests/:id` отсутствие поля
сохраняет его текущее значение. Явный `null` разрешён только для
`departmentId` (убрать отдел) и `maxAttempts` (снять лимит попыток).
Примеры JSON body:

| Маршрут | Body | Результат |
|---|---|---|
| `/admin/users/:id` | `{"fullName":"Иван Петров"}` | Меняется ФИО; отдел, часовой пояс и активность сохраняются |
| `/admin/users/:id` | `{"departmentId":null}` | Сотрудник больше не состоит в отделе |
| `/admin/tests/:id` | `{"showCorrectAnswers":false}` | Выключается разбор; лимит попыток и проходной балл сохраняются |
| `/admin/tests/:id` | `{"passScore":0}` | Проходной балл становится 0; остальные настройки сохраняются |
| `/admin/tests/:id` | `{"maxAttempts":null}` | Попытки становятся безлимитными |

`null` для остальных полей, пустой body и неверные типы отклоняются
с 400 `invalid_request` без частичного изменения. `false` и `0` остаются
значениями, а не признаком отсутствия. CSRF Origin, сессия и роль
администратора обязательны. Отключение сотрудника по-прежнему отзывает
сессии и приглашения в той же транзакции; ошибка FK откатывает весь PATCH.

Добавлено 11 PostgreSQL/API-проверок: сохранность всех столбцов и
credentials, замена/очистка/повторная очистка/восстановление nullable полей,
значения false/0, запрет null в обязательных полях, откат FK и контроль
доступа. Новых миграций нет; обычная сборка и restart сервера.
Другие PATCH-маршруты в H13 не менялись.

## CSRF и адрес приложения (H12)

Корневой onRequest hook проверяет все методы, кроме GET/HEAD/OPTIONS,
до парсинга body, авторизации, auth rate counters и бизнес-операций.
Требуется ровно один `Origin`, равный настроенному `APP_ORIGIN`.
Чужой/соседний поддомен, другой порт/протокол, `null`, список значений,
неправильный или отсутствующий Origin дают 403 `csrf_forbidden` без
изменения сессии/данных. Защищены также login, invite check/accept/logout,
multipart, события, попытки теста, push и будущие вложенные маршруты.
GET/HEAD/OPTIONS всё равно подчиняются обычной авторизации своих routes.
Действия, меняющие учебные/пользовательские данные, не должны использовать GET.

Доверенный адрес берётся из конфигурации при старте, не из Host,
X-Forwarded-Host/Proto, Referer или Fetch Metadata. SameSite=Lax/Secure
cookie и роль продолжают проверяться отдельно. Referer fallback и исключение
для loopback не добавлены; CORS не включён. Проверка относится к браузерной
CSRF-модели: HTTP-клиент может указать Origin сам и всё равно должен иметь
действующую сессию/роль. Эта мера не защищает от выполнения чужого кода
внутри самого origin приложения.

### Обязательно перед первым production-деплоем H12

1. На сервере откройте файл из `EnvironmentFile` вашего lms.service.
   В примере репозитория это `/opt/lms/server/.env`:

   ```bash
   nano /opt/lms/server/.env
   ```

2. Добавьте строку ниже, заменив `edu.example.ru` **реальным HTTPS-адресом
   LMS из адресной строки браузера** (тем же доменом, что в Nginx):

   ```dotenv
   APP_ORIGIN=https://edu.example.ru
   ```

   Только схема/хост/необязательный порт, без `/api`, path, query, fragment,
   логина/пароля и wildcard. Нельзя использовать домен другого проекта.
   Один canonical origin; заходить на приложение нужно через него.

3. Сохраните файл и выполните обычное обновление/сборку/restart.
   Новой миграции H12 нет. `deploy/deploy.sh` проверяет APP_ORIGIN из
   server/.env после сборки сервера, до публикации клиента/restart.
   При пустом/неправильном/HTTP-адресе production запуск отказывается
   работать. Проверки `/health` и `/health/db` в deploy.sh сохраняются.

Для разработки `.env.example` содержит `http://localhost:5173`; без значения
вне production используется тот же origin. Для другого Vite-порта или
127.0.0.1 задайте точный адрес браузера в APP_ORIGIN. Nginx/Vite должны
передавать исходный Origin без подмены; текущие примеры proxy с этим совместимы.
Обновлять сервер и клиент вместе: Beacon теперь передаёт application/json Blob,
сохраняя Origin при no-referrer, и не очищает очередь, если браузер отказался
поставить запрос в отправку. Подтверждение записи сервером и дедупликация
событий остаются отдельной задачей DEV-10.

После обновления можно проверить guard без входа/чужих данных:

```bash
# 403 csrf_forbidden — без Origin
curl -i -X POST http://127.0.0.1:3000/auth/logout
# 200 ok — замените origin тем же фактическим адресом, что в server/.env
curl -i -X POST http://127.0.0.1:3000/auth/logout -H 'Origin: https://edu.example.ru'
```

Добавлены 8 HTTP/config-проверок без БД, проверка реального pagehide/Blob
и 8 PostgreSQL/API-сценариев: отказ до изменений/счётчиков, нормальный
login/invite/редактор/upload/events/test flow и сохранение авторизации.
VDS/его env не менялись в этой задаче. Основание политики:
[OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html),
[Fetch Origin](https://fetch.spec.whatwg.org/#append-a-request-origin-header),
[Beacon](https://www.w3.org/TR/beacon/#sendbeacon-method).

## Безопасные пути вложений (SEC-04)

Новые вложения сохраняются как `<UUID>.<разрешённое расширение>`; оригинальное
имя хранится в БД для интерфейса и скачивания. До создания каталога сервер
проверяет UUID и существование урока. Запись, скачивание и удаление проверяют
границы каталога урока и символьные ссылки. Файлы открываются без перехода
по ссылке; новая запись не перезаписывает существующий файл.

Обычные ранее загруженные файлы с именем `<UUID>-<оригинальное имя>` работают
без переноса и миграции БД. Пути вне каталога урока и символьные ссылки
отклоняются. `UPLOAD_DIR` и его подкаталоги должны быть настоящими каталогами
и быть доступны для изменения только сервису LMS. Новые каталоги создаются
с правами 0700, файлы — 0600; права существующих каталогов не меняются.
Проверки не заменяют права ОС: другой процесс с правами пользователя LMS
может менять каталоги между проверкой и операцией. Пример systemd-сервиса
запускается под отдельным пользователем `lms` с ограничением ReadWritePaths.

В CI добавлены 10 сценариев API загрузки/скачивания/удаления и 11 проверок
хранилища: traversal-имена, неверный/неизвестный урок, symlink, старые файлы,
права доступа к курсу и очистка слишком большой загрузки. Быстрая проверка
хранилища без PostgreSQL (из корня):

```bash
node --test --import tsx server/tests/storage.test.mjs
```

Временная запись и очистка при ошибках описаны в H14 ниже. Квоты и полная
согласованность файловой системы/БД (DEV-05) остаются отдельными задачами.

## Надёжность загрузки вложений (H14)

Загрузка пишет в приватный `.upload-<UUID>.part` в каталоге урока. После
завершения потока и проверки формата сервер повторно проверяет урок в
короткой транзакции с `FOR NO KEY UPDATE` (с H15): удаление урока/каскадное удаление
ожидает завершения публикации и INSERT. Во время приёма файла и работы
parser-а блокировка БД не удерживается. Если урок уже удалён, возвращается
404 `lesson_not_found`, временный файл удаляется.

Маршрут использует событийный интерфейс Busboy с синхронной установкой
обработчика ошибки потока, до mkdir/open. Это закрывает обрыв multipart
ещё до возврата async `req.file()`. Ожидается завершение всего multipart,
а не только потока первого файла. Принимается одна file part без остальных
полей; дополнительные файлы/поля дают 413 `payload_too_large`. Текущий
клиент отправляет именно один файл. Busboy 3.2.2 закреплён как прямая
зависимость; версия уже присутствовала в lockfile, обновления parser-а нет.

Проверенный файл публикуется под прежним `<UUID>.<ext>` через hard link
в том же каталоге: окончательное имя появляется атомарно, существующий
файл не перезаписывается. Затем временное имя удаляется и строка вложения
сохраняется в БД. Хранилище должно поддерживать hard links (обычная локальная
Linux FS на VDS); при отказе публикации INSERT не выполняется. Старые
файлы и их пути в БД не меняются; новой миграции нет.

Сбой потока, проверки содержимого, подключения или SQL до COMMIT вызывает
очистку временного и созданного окончательного файла. Ошибка close или
одного unlink не мешает остальным попыткам очистки. Очистка не удаляет файл,
с которым произошло столкновение имени. Если очистка не удалась, лог
содержит только фиксированные event/category `upload/cleanup_failed`.

При ошибке подтверждения COMMIT окончательный файл сохраняется: транзакция
могла уже завершиться, и удаление сломало бы существующую запись БД.
API возвращает безопасную ошибку, лог — `upload/commit_uncertain` без SQL,
пути и текста исключения. Перед повторной загрузкой оператор должен сверить
список вложений урока/записи `lesson_attachments` и файлы, чтобы не создать
дубликат. При остановке процесса/ОС finally не гарантирован; это не общая
атомарная транзакция между БД и файловой системой.

Добавлено 13 проверок staging/receiver без БД и 9 PostgreSQL/API-сценариев: публикация,
коллизия/symlink, ошибки потока/close/unlink, ошибки подключения/SQL,
потеря подтверждения COMMIT, обрыв multipart и конкурирующее удаление урока.
Проверить без PostgreSQL из корня:

```bash
node --test --import tsx server/tests/upload-staging.test.mjs server/tests/upload-receiver.test.mjs
```

H14 закрывает временную загрузку и обработку ошибок. Полный DEV-05 остаётся
открытым: квоты, ограничения параллельных загрузок, мониторинг свободного
места, сверка/уборка сирот после аварии, надёжная очередь удаления файлов.
Текущие DELETE урока/модуля/курса каскадно удаляют строки вложений в БД,
но файлы на диске сохраняются; H14 не меняет эти маршруты. Пока очередь
удаления не внедрена, удалённый контент требует отдельной сверки хранилища.

## Целостность контента и назначений (H15 / DEV-09)

Миграция `1700000014000_content_integrity.cjs` добавляет UNIQUE
`tests(scope,parent_id)` и две generated FK-колонки для модуля/урока.
Существование родителя проверяется API и БД, включая прямые SQL writes;
удаление урока/модуля/курса каскадно удаляет его тесты, вопросы, ответы
и попытки. Журнал событий остаётся. Это продолжает существующий каскад
DELETE теста; закрытие доступа по сроку по-прежнему сохраняет результаты.
Политика сохранения удалённого контента/версий здесь не вводится.

Позиции модулей, уроков, вопросов и вложений уникальны внутри своего
родителя и неотрицательны. Append/reorder используют одну блокировку
`FOR NO KEY UPDATE` родителя до COMMIT; FK checks совместимы с этой
блокировкой. Для модулей/уроков reorder принимает только полный набор
ID детей указанного courseId/moduleId. Дубли (включая UUID с разным
регистром), неизвестные/чужие ID — 400; неполный устаревший список — 409;
отсутствующий родитель — 404. Повторно загрузите дерево при конфликте.
Перестановка временно откладывает UNIQUE до COMMIT; ошибка откатывает всё.
Создание одного теста возвращает 201, конфликт — 409 `test_already_exists`.

Массовое назначение сохраняет существующий UNIQUE(user_id,course_id)
и upsert: обновляет дедлайн/обязательность/источник, сохраняет прогресс и
completed. Состав группы/отдела читается одним запросом в транзакции;
это снимок состава на момент чтения. ID сотрудников обрабатываются в
едином порядке, чтобы пересекающиеся назначения не брали row locks в
обратной последовательности. Назначения и их assignment_created events
фиксируются одной транзакцией; поздний FK/SQL/event failure откатывает
новые строки, прежние обновления и весь журнал этой операции. Повторный
успешный запрос по-прежнему пишет события; идемпотентные request keys
и дедупликация клиентских событий остаются отдельными задачами.

Схемы добавлены к create module/lesson, reorder и bulk assignment: UUID,
массив ID, JSON boolean, запрет лишних полей. Названия module/lesson —
непустые до 1000 символов без NUL; reorder — до 10 000 ID. Другие поля/
маршруты courses/assignments не получают здесь полного набора SEC-11 схем.

## Содержимое вложений (SEC-05, проверка формата)

Разрешённые расширения и предел 50 МиБ сохранены. Перед записью в БД сервер
проверяет байты завершённой загрузки. Неверный формат, повреждение, ошибка
парсера или превышение его лимитов дают `400 file_content_not_allowed`;
временный файл удаляется, вложение не публикуется.

- PDF: сигнатура, конец файла и разбор структуры документа с непустым
  деревом страниц. Зашифрованные PDF не принимаются.
- PNG: заголовок, размеры, границы и CRC чанков, IDAT/IEND. JPEG: сигнатура,
  границы заголовочных сегментов, кадр с размерами, SOS и конечный EOI.
  Это структурные проверки, без полного декодирования изображения.
- DOC/XLS: сигнатура и разбор OLE-контейнера, затем WordDocument с FIB/table
  либо Workbook/Book с BIFF BOF. Зашифрованный Word не принимается.
  Все записи внутреннего формата Word/Excel не валидируются.
- DOCX/XLSX: ZIP с корректными обязательными Content Types, package
  relationships и основным XML нужного типа/namespace. Папка word/ или xl/
  сама по себе недостаточна. Проверяются размер распакованных читаемых
  частей и CRC; DTD/entities запрещены. Архив не извлекается на диск.

Клиентский MIME не заменяет проверку байтов. Если он указывает другой
известный разрешённый формат, загрузка отклоняется; неизвестный MIME или
`application/octet-stream` не дают обхода проверки.

Парсеры работают в отдельном worker с тайм-аутом 5 секунд и пределом
JS-heap 128 МиБ (это не предел всей памяти процесса/Buffer). Для PDF decoder:
до 16 МиБ на распакованный поток, суммарный бюджет выделения буферов
64 МиБ; лимит проверяется до выделения. Адаптер использует внутренний
DecodeStream зафиксированной версии pdf-lib 1.17.1: при обновлении
обязательны положительные и resource-limit regression-проверки.
Для Office ZIP:
не более 4096 записей, суммарный заявленный распакованный размер до 200 МиБ,
метаданные до 1 МиБ каждое, основной XML до 16 МиБ. Зашифрованные ZIP,
дубликаты имён и неподдерживаемые методы сжатия отклоняются. Документы,
которые невозможно проверить в этих границах, необходимо загрузить
в другом допустимом формате.

Скачивание сохраняет `Content-Disposition: attachment`, устанавливает
серверный `Content-Type` и `X-Content-Type-Options: nosniff`, проверяет
авторизацию и доступ к курсу. Ранее загруженные файлы не перепроверяются
и продолжают скачиваться. `UPLOAD_DIR` должен находиться вне web-root
клиента; пример Nginx дополнительно запрещает `/uploads/`. API не имеет
публичного статического маршрута для файлов.

Проверка формата не гарантирует отсутствие вредоносного содержимого:
PDF может содержать скрипты, DOC/XLS — макросы. Общая политика макросов,
антивирус и карантин остаются незакрытой частью SEC-05; это изменение
их не внедряет. Макроформаты DOCM/XLSM не входят в разрешённый список.
Быстрые проверки без БД:

```bash
node --test --import tsx server/tests/storage.test.mjs server/tests/file-content.test.mjs
```

## Ограничение попыток входа (SEC-06)

Перед bcrypt сервер проверяет счётчики в PostgreSQL. Счётчики общие для
экземпляров приложения и сохраняются при перезапуске. Окно — 10 минут
от первой попытки; учитываются и успешные, и неудачные запросы. Известный
email и неизвестный email ограничиваются одинаково до проверки учётной
записи. Ключ email приводится к нижнему регистру и обрезается по краям;
это нормализация счётчика, существующий поиск пользователя не меняется.

| Запросы | Ключ | Лимит за окно |
|---|---|---:|
| Вход и принятие приглашений вместе | IP | 100 |
| Вход | Нормализованный email | 10 |
| Принятие приглашения | Токен и пользователь действующей ссылки | По 10 |
| Проверка приглашения POST | IP, отдельный счётчик | 120 |

Порог задаётся константами в `server/src/auth/rate-limit.ts`. IP-порог
учитывает общий NAT примерно 50 сотрудников. Разные IP не сбрасывают
email-порог; разные действующие ссылки одного сотрудника не сбрасывают
его порог принятия приглашений. Превышение даёт `429 rate_limited`,
`Retry-After` в секундах и `retryAfterSeconds` в JSON. Отклонённые запросы
не продлевают окно. `is_active` и пароль не меняются из-за ограничения;
после истечения окна попытки снова доступны. Уже открытая сессия работает.

Для текущего размещения с одним Nginx на том же сервере доверяется только
последний адрес в X-Forwarded-For от точного loopback peer: 127.0.0.1,
::1 или IPv4-mapped 127.0.0.1. Nginx example добавляет `$remote_addr` через
`$proxy_add_x_forwarded_for`; пользовательский префикс игнорируется.
Прямые внешние подключения не могут сменить IP заголовком. IPv6
канонизируется, IPv4-mapped адреса объединяются с IPv4. При другой
топологии proxy сначала требуется изменить и проверить правило доверия;
`trustProxy: true` для этой защиты не используется.

В auth_rate_limits хранятся SHA-256 ключи, счётчик и срок окна, без сырого
email/IP/токена. Это псевдонимизация, не гарантия анонимности. Истёкшие
записи удаляются при защищённых запросах, не чаще раза в минуту и партиями
до 1000. При отсутствии таких запросов очистка ждёт следующего обращения;
при большом числе ключей потребуется отдельная регулярная очистка.
Сбой БД/отсутствие таблицы блокирует попытку, обхода ограничения нет.
Первый отказ каждого счётчика в окне пишет структурированный warning
`auth_rate_limited` со scope и временем ожидания, без субъекта/секретов.
Request-логи и приватные ответы защищены в SEC-07 (см. ниже).

Вход и принятие приглашения ограничены JSON body 8 КиБ. Email должен
быть строкой до 254 символов, пароль входа — непустой строкой до 1024
символов/4096 UTF-8 байт. Это сохраняет вход с длинными старыми паролями,
которые bcrypt ранее усекал. Новый пароль: от 8 символов и до 72 UTF-8
байт, чтобы bcrypt не усекал его незаметно. Токен: 1–128 символов
base64url (у выпускаемых сейчас токенов длина 43). Неверные типы не преобразуются в строки.
Формы показывают сообщение об ожидании, повторная отправка блокируется.

Перед запуском обновлённого сервера обязательна миграция
`1700000013000_auth_rate_limits.cjs`. Из корня checkout приложения на VDS,
где уже настроен `server/.env` с рабочим DATABASE_URL:

```bash
npm ci
npm run migrate --workspace server
npm run build
```

После этого можно перезапускать сервис обычным способом. Существующий
`deploy/deploy.sh` уже применяет миграции до перезапуска. Откат миграции
удалит счётчики и допустим только после отката кода. Быстрая проверка IP
без PostgreSQL:

```bash
node --test --import tsx server/tests/auth-client-ip.test.mjs
```

## Восстановление доступа и отзыв сессий (SEC-08)

Повторное приглашение — восстановление пароля (SPEC §2). Новая ссылка
отзывает все предыдущие неиспользованные ссылки этого пользователя.
Пароль и открытые сессии сохраняются до фактического принятия ссылки.
При принятии в одной транзакции меняется пароль, помечается использованная
ссылка, отзываются остальные неиспользованные ссылки, удаляются все старые
сессии, создаётся одна новая сессия и событие session_start. При ошибке
любой записи все изменения откатываются. Другие пользователи не меняются.

При отключении через `PATCH /admin/users/:id` с `{"isActive":false}` в той
же транзакции отзываются ссылки и сессии. Повторное включение не возвращает
старые токены. Отключённому пользователю выпуск запрещён (409 user_inactive),
проверка и принятие legacy-ссылки тоже запрещены; приглашение больше не
присваивает is_active=true. Для восстановления сначала явно включите
аккаунт этим же admin API с `{"isActive":true}`, затем выпустите новую ссылку.
Выпуск для отсутствующего UUID возвращает 404 user_not_found. Админка
отключает кнопку для неактивных пользователей, блокирует повторный клик
на время запроса и объясняет отзыв предыдущих ссылок/сессий.

Выпуск, принятие, отзыв ссылки, вход и создание сессии используют общий
lock строки пользователя до lock приглашений/сессий. При входе lock держится
от чтения hash до проверки пароля/создания сессии: старый пароль не может
создать действующую сессию после одновременного reset. Используется READ
COMMITTED явно и FOR NO KEY UPDATE: FK-проверки created_by не вызывают
cross-user deadlock. Отключение берёт тот же lock через UPDATE. Истечение
приглашения проверяется по clock_timestamp после ожидания и после bcrypt.

Новой миграции нет: legacy-ссылки поддержаны; первая успешная смена пароля
отзовёт остальные. Уже принятые ссылки/история сохраняются. Все экземпляры
сервера нужно обновить, затем выполнить обычный restart; смешивать старый
и новый auth-код нельзя. Отзыв блокирует последующие запросы; уже начатые
авторизованные запросы этим изменением не отменяются. Старые вкладки
потребуют повторного входа; push_subscriptions и учебные данные не удаляются.

22 новых PostgreSQL/API-теста проверяют отзыв/изоляцию, inactive/reenable,
legacy links, обе последовательности login/reset, issue/reset и
reset/deactivation, конкурентные приложения/created_by FK, expiry во время
ожидания/после hash и rollback при сбое вставки/event/cleanup. Гонки
управляются настоящими PostgreSQL-locks и проверкой pg_blocking_pids,
без mock БД, глобальных trigger/DDL и изменений рабочих данных.

## Приглашения, приватные ответы и логи (SEC-07)

Новые ссылки — `/invite#<token>`: fragment не отправляется HTTP-серверу.
Клиент считывает token один раз до React/StrictMode, очищает текущую запись
истории до `/invite` и держит token только в памяти. Старые `/invite/<token>`
работают с новым клиентом; их первый запрос всё ещё приходит прокси с token.
После перезагрузки очищенного экрана нужно снова открыть исходную ссылку.
Автоперезагрузка при обновлении SW на экране приглашения отключена.

API проверки/принятия — фиксированные POST `/auth/invitations/check` и
`/auth/invitations/accept`; token находится в JSON body, лимиты SEC-06
сохранены. API с token в пути удалён: старому клиенту требуется обновление.
Сервер и клиент нужно разворачивать вместе. Все ответы Fastify, включая
401/403/404/429/500, JSON parser errors, отчёты и скачивания, получают
`Cache-Control: no-store` и `Referrer-Policy: no-referrer`. Fetch также
использует эти политики; SW продолжает кешировать только общую оболочку.
В HTML есть referrer meta, в том числе для предкешированной оболочки.

Request logger пишет метод и шаблон маршрута, response logger — статус.
Unknown URL не пишется. Body/headers/cookies/пароли/token удаляются из
известных структурированных полей; errors пишутся с фиксированным типом
без message/stack/detail/cause. Pino hook также исключает копирование
err.message в msg. Не добавляйте свободные сообщения или произвольные
вложенные telemetry-объекты с секретами: redaction не угадывает содержание.
CLI `npm run invite` намеренно выдаёт секрет администратору в stdout;
не перенаправляйте этот вывод в общие логи.

Nginx: обновите действующий vhost по `deploy/nginx.conf.example` (сохранив
свой домен, сертификаты и пути). Активные map/log_format находятся внутри
http{}; access_log не пишет query/Referer/User-Agent/body/credentials.
Старые invitation URL маскируются. Error log имеет уровень warn, без debug.
Для API и старых invitation locations error_log направлен в /dev/null: Nginx
не позволяет редактировать поля стандартного error_log, включая Referer
при upstream error. Для диагностики остаются статусы/время upstream в
безопасном access log и очищенный logger приложения. Старый API
возвращает 410 без upstream. Оболочка старой ссылки отдается без internal
redirect, чтобы ошибка чтения не переключила logging context. Для `/api/`
proxy_cache выключен явно, no-store/no-referrer добавлены даже при 502.

После изменения конфигурации на VDS выполните `sudo nginx -t`, затем
`sudo systemctl reload nginx`. `deploy.sh` не устанавливает vhost автоматически.
В CI `deploy/test-nginx-privacy.py` запускает настоящий Nginx с временными
файлами/local upstream: проверяет POST, старые/encoded ссылки, 404/410/502,
заголовки и отсутствие тестового token в access/error logs.

Для файлов Nginx установите `deploy/logrotate-lms.example` как
`/etc/logrotate.d/lms`: daily, максимум 7 дней, права 0640 www-data:adm;
убедитесь, что этот путь не покрыт другим правилом logrotate. Файлы и
резервные копии прежних логов могут уже содержать token — ограничьте доступ
и удалите по принятой политике хранения. Для stdout сервиса в journald
отдельно установите лимит хранения (например MaxRetentionSec=7day в
journald.conf/drop-in; это действует на весь journal) и права чтения.
Не включайте debug/body logging, capture payloads в APM или перехват
секретов расширениями браузера. Production-конфигурация, старые логи и
сторонние telemetry-системы не проверялись и не менялись этим PR.

и сразу логинит (cookie `lms_session`). Дальше — `POST /auth/login`,
`POST /auth/logout`, `GET /auth/me`.

## Админка (этап 3)

```bash
cd client && npm install && npm run dev
```

Откройте http://localhost:5173 — экран входа. Войдите под администратором,

## Тесты (этап 5)

## Назначения и дедлайны (этап 6)

Вкладка «Назначения»: выбрать курс, назначить сотруднику/группе/отделу,
задать дедлайн. Доступ закрывается непосредственно при запросе по времени
PostgreSQL (`deadline <= clock_timestamp()`), даже если планировщик не
работает. Фоновая проверка раз в минуту фиксирует status → overdue,
closed_at и access_closed для assigned/in_progress. Перенос срока в
будущее или снятие срока возвращает доступ; перенос в прошлое — нет.
Ручной запуск проверки: POST /admin/assignments/run-deadline-check.

Проверяется структура курса, урок, скачивание вложения, история/старт
попытки, сохранение ответа и завершение теста. Просроченные операции
возвращают 403 deadline_passed до выдачи материалов или записи ответов/
результатов. «Мои курсы» сразу показывает overdue в ответе API без изменения
сохранённого статуса. Самозапись в каталог не обновляет существующее
назначение и не позволяет обойти срок.

Завершённый курс подчиняется тому же сроку (SPEC §5.1): после дедлайна
доступ закрыт, сохранённый completed, ответы, баллы и журнал не удаляются.
После переноса срока доступ к материалам и истории возвращается.
NULL не ограничивает срок; сохранённый overdue остаётся блокирующим до
admin extension. Учётная запись и другие курсы не закрываются; администратор
сохраняет доступ. Часы Node не используются для проверки срока.

Новой миграции для SEC-09 нет. Обновить и перезапустить все экземпляры
сервера; VDS в этой задаче не менялся. Проверка выполняется при обработке
запроса и не отменяет уже начатые запросы/скачивание или открытый видеоплеер.
Защита видео, DEV-08 (конец дня по часовому поясу) и DEV-01 (целостность
вопросов/вариантов, гонки попыток) остаются отдельными задачами.
Добавлены 19 PostgreSQL/API-сценариев, включая реальное пересечение срока
без job, сдвиг часов Node, все операции теста, перенос и изоляцию.

## Защита планировщиков (H16 / DEV-07)

Дедлайны, отчёты и уведомления используют отдельные PostgreSQL session
advisory locks с фиксированными ключами. Каждый backend, ручная проверка и
формирование отчётов при входе администратора проходят через один runner.
Занятая job пропускается фоновым таймером; ручной API возвращает
`409 {"error":"job_in_progress"}`. Разные типы jobs могут выполняться параллельно.
Блокировки требуют одной PostgreSQL БД и session pooling (обычный node-pg
pool поддерживается); transaction pooling PgBouncer для этого runner не подходит.

Таймер запускает следующую проверку через интервал **после завершения** текущей:
дедлайны — 1 минута, отчёты — 5 минут, уведомления — 1 час. Первая проверка
выполняется сразу после успешного запуска HTTP-сервера. Ошибка не выключает
следующие проверки; занятую job таймер тоже проверит на следующем цикле.

Изменение статуса просрочки и запись `access_closed` теперь атомарны.
Отчёт за дату и весь докатываемый диапазон сохраняются одной транзакцией;
ошибка оставляет прежние данные и позволяет повторить запуск. Все запросы
отчёта, включая аналитику, используют выделенное соединение runner.
Дневной флаг в памяти удалён: курсор определяется только сохранёнными
отчётами. Существующая политика UTC, начальное окно 14 дней и выбор
`max(report_date)` сохранены; старые неполные даты/пропуски автоматически
не исправляются, их можно пересобрать вручную.

Правила по умолчанию и записи уведомлений сохраняются атомарно. Push
начинается только после COMMIT, а session lock остаётся до завершения
отправки. Повторная проверка учитывает сохранённые уведомления: для overdue —
назначение/тип/канал за всё время, для остальных — за день БД, как раньше.
Это предотвращает конкурентные повторы текущих jobs, но **не гарантирует
доставку push ровно один раз**: падение после COMMIT до отправки или ошибка
транспорта оставляют запись без автоматического повтора. Устойчивая outbox,
ключ правила/версии назначения, retry/backoff и мониторинг доставки остаются
открытой частью DEV-07. Таймаут web-push 10 секунд ограничивает бездействие
сокета, а не общую длительность отправки; длительность shutdown также
зависит от активных запросов к PostgreSQL и push-провайдеру.

SIGINT/SIGTERM закрывают Fastify, останавливают таймеры, запрещают новые jobs,
ожидают уже начатые (включая login и отправку push), затем закрывают pool.
При ошибке unlock/соединения выделенная сессия уничтожается вместо возврата
в pool. При аварийном завершении процесса PostgreSQL освобождает session lock
после разрыва соединения. Журнал runner содержит только тип job, результат
и длительность, без SQL/ошибок драйвера/ID пользователей/токенов.

Новой миграции H16 нет. Тесты используют отдельную случайную схему и ключи
advisory lock, чтобы не затрагивать данные остальных проверок. VDS автоматически
не обновляется; предыдущая миграция H15 по-прежнему входит в обычный deployment.


## Серверная модель попыток (H17 / DEV-01)

API истории/старта/ответов/завершения проверяет UUID, JSON-типы, уникальность
выбранных ID и отсутствие лишних полей. Пустой POST старта/завершения
поддерживается. Response DTO исключают внутренние поля; до завершения
нет правильных вариантов ни в вопросах, ни в ответе на сохранение.
Разбор появляется только при актуальном `show_correct_answers=true`.

Старт сначала возобновляет открытую попытку, даже если она последняя
разрешённая. Лимит применяется только к созданию новой: считается число
сохранённых попыток; номер — прежний максимальный + 1. Параллельные старты
одного сотрудника получают одну открытую попытку и один стартовый event.
Сохранение принимает только вопрос текущего теста и его варианты; для
single-choice — максимум один. Пустой выбор допустим, но неверен.
Неверные/чужие варианты или дубли UUID с разным регистром — 400; чужая
попытка — 404. Превышение лимита — прежний 409 `no_attempts_left`.

Согласно SPEC §3–4, версионность не вводится: правки администратора видны
сразу. При продолжении открытой попытки возвращаются текущие вопросы и
существующие варианты выбора. При завершении сервер заново сравнивает
выбранный набор с текущим набором верных вариантов; сохранённый `is_correct`
не считается доказательством. Добавленный вопрос участвует в знаменателе,
удалённый — исчезает из него; удалённый выбранный вариант не даёт балл.
Вопрос оценивается «всё или ничего», пропущенный — неверный, итог округляется
до целого процента. Применяются текущие pass_score/show_correct_answers.
Законченный score/passed повторно не рассчитывается: answer/finish возвращают
409 `attempt_already_finished`, повторного finish event нет. DELETE самого
теста/курса по-прежнему каскадно удаляет попытки, как описано в H15.

Пустой тест, вопрос без верного варианта, несколько верных у single-choice
или некорректные настройки не расходуют новую попытку: 409 `test_not_ready`.
Если администратор временно сделал открытую попытку некорректной, он должен
исправить тест, после чего сотрудник сможет продолжить её.

Запросы используют короткую транзакцию и порядок locks: сотрудник
`FOR NO KEY UPDATE` → тест `FOR SHARE` → открытая попытка `FOR NO KEY UPDATE`.
Все изменения вопросов/вариантов в редакторе берут `FOR NO KEY UPDATE`
теста. Разные сотрудники могут проходить тест одновременно; правка ждёт
завершения текущего запроса, а не всей попытки. Доступ/активность повторно
проверяются после ожидания; дедлайн — по времени PostgreSQL перед записью.
Это не отменяет уже зафиксированные операции при последующем истечении
срока. Состояние и start/answer/end event коммитятся вместе; сбой event/SQL
откатывает всё. Успешное повторное сохранение ответа пока пишет новый
question_answered event; request idempotency/dedup остаются DEV-10.

Миграция `1700000015000_attempt_integrity.cjs` добавляет UNIQUE
(test_id,user_id,attempt_number), partial UNIQUE одной in_progress попытки
на сотрудника/тест, положительный номер, score 0…100 и согласованность
status/finished_at/score/passed. Она сохраняет существующие ID/результаты
и не объединяет/не удаляет конфликтующие попытки. Проблемная история
останавливает migration: её надо отдельно согласовать и исправить.
`down` снимает ограничения, строки сохраняются.
