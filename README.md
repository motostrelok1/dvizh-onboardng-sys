# LMS

## Автоматические проверки (CI)

GitHub Actions запускает `.github/workflows/ci.yml` для каждого PR, при
обновлении `main` и вручную через **Actions → CI → Run workflow**.
Используется Node.js 24 (версия зафиксирована в `.nvmrc`) и установка
из корневого `package-lock.json` через `npm ci`.

Две проверки работают независимо:

- **Server and client build** — TypeScript сервера и клиента, Vite и PWA.
- **PostgreSQL and auth tests** — отдельная PostgreSQL 16, все миграции,
  повторный запуск миграций и 51 тест (30 через Fastify inject,
  11 для файлового хранилища и 10 для содержимого файлов).

Тесты проверяют 401/403, роли, вход/выход, истечение сессии, блокировку
существующей сессии после отключения сотрудника (SEC-01), Secure-cookie
в production (SEC-02), одноразовые/отозванные/просроченные приглашения и
изоляцию назначенного курса между пользователями. Они используют настоящие
маршруты и SQL. Рабочая БД и production-секреты для CI не нужны.
Тесты попыток, конкурентных запросов и интерфейса — следующие
задачи; этот набор пока не покрывает все функции LMS.

Локальная сборка (из корня репозитория):

```bash
npm ci
npm run build
```

Локальные интеграционные тесты требуют отдельную локальную PostgreSQL с
базой `lms_test`. Создайте её отдельно от рабочей базы; подставьте своего
пользователя и URL-кодированный пароль в следующую команду:

```bash
export TEST_DATABASE_URL='postgres://TEST_USER:URL_ENCODED_PASSWORD@127.0.0.1:5432/lms_test'
DATABASE_URL="$TEST_DATABASE_URL" npm run migrate --workspace server
npm test
```

`npm test` не читает `.env`, не использует рабочую `DATABASE_URL` и
отказывается запускаться без `TEST_DATABASE_URL`, локального адреса и
имени базы с окончанием `_test`. Тестовые данные имеют случайные UUID;
очистка удаляет только собственные записи, без `TRUNCATE`.

Перед слиянием PR откройте **Checks** и дождитесь успеха обеих проверок.
CI сам не сливает PR и не развёртывает приложение. Для обязательного
запрета слияния при ошибке проверки отдельно настройте защиту `main` с
этими двумя проверками; один workflow не включает защиту ветки.

## Безопасные пути вложений (SEC-04)

Новые вложения сохраняются как `<UUID>.<разрешённое расширение>`; оригинальное
имя хранится в БД для интерфейса и скачивания. До создания каталога сервер
проверяет UUID и существование урока. Запись, скачивание и удаление проверяют
границы каталога урока и символьные ссылки. Файлы открываются без перехода
по ссылке; новая запись не перезаписывает существующий файл.

Обычные ранее загруженные файлы с именем `<UUID>-<оригинальное имя>` работают
без переноса и миграции БД. Пути вне каталога урока и символьные ссылки
отклоняются. `UPLOAD_DIR` и его подкаталоги должны быть настоящими каталогами
и быть доступны для изменения только сервису LMS. Новые каталоги создаются
с правами 0700, файлы — 0600; права существующих каталогов не меняются.
Проверки не заменяют права ОС: другой процесс с правами пользователя LMS
может менять каталоги между проверкой и операцией. Пример systemd-сервиса
запускается под отдельным пользователем `lms` с ограничением ReadWritePaths.

В CI добавлены 10 сценариев API загрузки/скачивания/удаления и 11 проверок
хранилища: traversal-имена, неверный/неизвестный урок, symlink, старые файлы,
права доступа к курсу и очистка слишком большой загрузки. Быстрая проверка
хранилища без PostgreSQL (из корня):

```bash
node --test --import tsx server/tests/storage.test.mjs
```

Квоты и полная согласованность файловой системы/БД (DEV-05) остаются
отдельными задачами.

## Содержимое вложений (SEC-05, проверка формата)

Разрешённые расширения и предел 50 МиБ сохранены. Перед записью в БД сервер
проверяет байты завершённой загрузки. Неверный формат, повреждение, ошибка
парсера или превышение его лимитов дают `400 file_content_not_allowed`;
временный файл удаляется, вложение не публикуется.

- PDF: сигнатура, конец файла и разбор структуры документа с непустым
  деревом страниц. Зашифрованные PDF не принимаются.
- PNG: заголовок, размеры, границы и CRC чанков, IDAT/IEND. JPEG: сигнатура,
  границы заголовочных сегментов, кадр с размерами, SOS и конечный EOI.
  Это структурные проверки, без полного декодирования изображения.
- DOC/XLS: сигнатура и разбор OLE-контейнера, затем WordDocument с FIB/table
  либо Workbook/Book с BIFF BOF. Зашифрованный Word не принимается.
  Все записи внутреннего формата Word/Excel не валидируются.
- DOCX/XLSX: ZIP с корректными обязательными Content Types, package
  relationships и основным XML нужного типа/namespace. Папка word/ или xl/
  сама по себе недостаточна. Проверяются размер распакованных читаемых
  частей и CRC; DTD/entities запрещены. Архив не извлекается на диск.

Клиентский MIME не заменяет проверку байтов. Если он указывает другой
известный разрешённый формат, загрузка отклоняется; неизвестный MIME или
`application/octet-stream` не дают обхода проверки.

Парсеры работают в отдельном worker с тайм-аутом 5 секунд и пределом
JS-heap 128 МиБ (это не предел всей памяти процесса/Buffer). Для Office ZIP:
не более 4096 записей, суммарный заявленный распакованный размер до 200 МиБ,
метаданные до 1 МиБ каждое, основной XML до 16 МиБ. Зашифрованные ZIP,
дубликаты имён и неподдерживаемые методы сжатия отклоняются. Документы,
которые невозможно проверить в этих границах, необходимо загрузить
в другом допустимом формате.

Скачивание сохраняет `Content-Disposition: attachment`, устанавливает
серверный `Content-Type` и `X-Content-Type-Options: nosniff`, проверяет
авторизацию и доступ к курсу. Ранее загруженные файлы не перепроверяются
и продолжают скачиваться. `UPLOAD_DIR` должен находиться вне web-root
клиента; пример Nginx дополнительно запрещает `/uploads/`. API не имеет
публичного статического маршрута для файлов.

Проверка формата не гарантирует отсутствие вредоносного содержимого:
PDF может содержать скрипты, DOC/XLS — макросы. Общая политика макросов,
антивирус и карантин остаются незакрытой частью SEC-05; это изменение
их не внедряет. Макроформаты DOCM/XLSM не входят в разрешённый список.
Быстрые проверки без БД:

```bash
node --test --import tsx server/tests/storage.test.mjs server/tests/file-content.test.mjs
```

## Запуск (разработка)

```bash
# В корне создать .env со строкой POSTGRES_PASSWORD=<сильный_уникальный_пароль>
# Файл .env не коммитить; пароль не должен содержать переводы строк.
docker compose up -d          # PostgreSQL доступен только на 127.0.0.1:5432

cp server/.env.example server/.env
# В server/.env заменить REPLACE_WITH_URL_ENCODED_PASSWORD тем же паролем,
# URL-кодируя специальные символы (например @ как %40, # как %23).
cd server && npm install
npm run migrate               # создать таблицы
npm run dev                   # http://localhost:3000/health

cd ../client && npm install && npm run dev  # http://localhost:5173
```

Откройте http://localhost:5173 — должно показать «Статус сервера: ok».
Проверка БД: http://localhost:3000/health/db
Список таблиц: http://localhost:3000/health/tables

## Проверка входа (пока нет админки)

```bash
npm run seed:admin -- "Имя Фамилия" admin@example.com
npm run invite -- <user_id из вывода выше>
```

Полученный токен открывается как `GET /auth/invitations/<token>` (проверка),
`POST /auth/invitations/<token>/accept` с `{"password":"..."}` задаёт пароль
и сразу логинит (cookie `lms_session`). Дальше — `POST /auth/login`,
`POST /auth/logout`, `GET /auth/me`.

## Админка (этап 3)

```bash
cd client && npm install && npm run dev
```

Откройте http://localhost:5173 — экран входа. Войдите под администратором,
созданным через `npm run seed:admin` (см. выше). На вкладках: сотрудники
(создание, отдел, часовой пояс, выпуск ссылки-приглашения), отделы, группы
(состав участников через чекбоксы).

## Курсы (этап 4)

Вкладка «Курсы» в админке: создание курса, статус/доступ, дерево
модуль → урок, порядок модулей и уроков (кнопки ↑/↓), у урока — текст,
видео (провайдер + ссылка/идентификатор) и дополнительные материалы
(загрузка файлов, разрешены pdf/doc/docx/xls/xlsx/png/jpg, до 50 МБ —
список и лимит настроятся, когда решится открытый вопрос из SPEC §18).

## Тесты (этап 5)

В редакторе курса у каждого модуля и у каждого урока — кнопка «+ добавить
тест» (не больше одного на модуль/урок). Внутри теста: настройки (число
попыток, показ правильных ответов, проходной балл), вопросы с чекбоксом
«несколько верных», варианты ответов с чекбоксом «верный».

## Назначения и дедлайны (этап 6)

Вкладка «Назначения»: выбрать курс, назначить сотруднику/группе/отделу,
задать дедлайн. Фоновая проверка (раз в минуту) закрывает доступ к курсу
по дедлайну (status → overdue); перенос дедлайна возвращает доступ.
Ручной запуск проверки: POST /admin/assignments/run-deadline-check.

## Кабинет сотрудника (этап 7a)

После входа приложение само определяет роль: админ видит админку,
сотрудник — «Мои курсы» (статус, дедлайн) и открытый каталог с кнопкой
«Записаться». Открыв курс, сотрудник видит модули и уроки (пока только
структуру — содержимое урока появится в этапе 7b). Доступ к просроченному
или неназначенному курсу блокируется с понятным сообщением.

## Урок (этап 7b)

Клик по уроку в курсе открывает его: видео (vimeo — iframe, self_hosted —
<video>, другие провайдеры — заглушка), текст, список материалов со
ссылкой на скачивание. Скачивание и сам урок проверяют доступ к курсу —
просроченный или неназначенный курс отдаёт понятную ошибку.

## Прохождение теста (этап 7c)

Клик по бейджу теста (у модуля или у урока) открывает тест: вопросы по
одному, radio/checkbox в зависимости от настройки «несколько верных»,
после последнего вопроса — результат и, если включено в настройках
теста, разбор по каждому вопросу с подсветкой верных и выбранных
вариантов. При исчерпании попыток — понятное сообщение вместо кнопки
«начать».

## Журнал событий (этап 8)

Сервер сам пишет события: вход/выход, попытки теста, ответы на вопросы,
скачивание материалов, назначение курса, перенос дедлайна, автозакрытие
по сроку — эти типы нельзя прислать с клиента напрямую. С клиента
принимаются только lesson_view_start/end (POST /events), с буферизацией
в localStorage и досылкой при восстановлении сети.

## Дашборд и карточка сотрудника (этап 9)

Админка теперь открывается на вкладке «Дашборд»: сводка (сотрудники,
активные за 7 дней, средний прогресс, просрочки), фильтры по отделу и
группе, таблица с прогрессом по каждому. Карточка сотрудника — курсы с
прогресс-баром (доля просмотренных уроков по журналу событий), сводная
статистика и человекочитаемый лог последних действий.

## Ежедневный отчёт и аналитика (этап 10)

При входе администратор автоматически докатывает отчёты за пропущенные
дни (до вчера включительно). Вкладка «Отчёты» — дата, фильтры по
отделу/группе, кнопка «Обновить», экспорт CSV, настройка режима
формирования (по входу / по расписанию / оба). Вкладка «Настройки» —
пороги шести правил аналитики (вкл/выкл, значения, сброс к дефолтам),
журнал изменений порогов, список проблемных вопросов. В редакторе курса
есть «Пороги аналитики курса» — переопределение значений для конкретного
курса. Флаги показываются в дашборде (счётчик на сотрудника) и в его
карточке.

Упрощение: границы «дня» в отчёте считаются в UTC, а не в часовом поясе
сотрудника — как и у дедлайнов (этап 6), это стоит доработать вместе.

## Уведомления и push (этап 11)

Правила уведомлений о дедлайнах настраиваются в «Настройках» (за N дней,
в день дедлайна, при просрочке; каналы «в приложении» и «push»; для всех
курсов или конкретного). По умолчанию засеваются правила за 7 и 1 день, в
день дедлайна и при просрочке. Проверка идёт раз в час, ручной запуск —
POST /admin/notification-rules/run-check.

Для push нужны VAPID-ключи: `cd server && npm run vapid:generate` и
добавить результат в `server/.env`. Без ключей push тихо отключён —
уведомления «в приложении» работают в любом случае. У сотрудника: колокольчик
в шапке, список уведомлений с отметкой «прочитано», кнопка «Включить
push-уведомления» (запрашивает разрешение браузера по клику).
