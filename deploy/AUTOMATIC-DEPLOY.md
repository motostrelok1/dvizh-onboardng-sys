# Автоматическое развёртывание после успешного CI

**Фактическая проверка 2026-10-15:** после PR #41 CI `38766575126` выполнил автоматическую публикацию `6362330`. После PR #42 CI `38768757644` автоматически обновил VDS до `29b627c`. Эти проверки подтверждены журналами Actions. Любой новый merge в `main` снова запускает этот процесс; если серверная проверка/миграции/lockfile несовместимы, деплой останавливается и требуется ручной rollout. Текущий список открытых проверок — [../docs/NEXT-STEPS.md](../docs/NEXT-STEPS.md).

После слияния PR в `main` workflow `CI` сначала выполняет сборку
frontend/backend и интеграционные тесты PostgreSQL. Только при успехе
обоих заданий job `Deploy to production after green CI` запускает
предварительно установленный на VDS скрипт
`/usr/local/sbin/lms-approved-deploy` с SHA проверенного коммита.

## Защита рабочего сервера

- Для PR деплой **не запускается**.
- Для пушей в `main` отмена выполняющегося CI отключена:
  текущий деплой нельзя прервать новым коммитом.
- Ручной и автоматический деплой используют общую группу блокировки
  `lms-production-deployment` и не выполняются одновременно.
- SSH подключается только как `lms-deploy` с проверкой known_hosts.
- Серверный root-owned скрипт выполняет полный backup БД, вложений и
  прежних файлов сборки, проверки health и попытку отката.
- Изменения миграций, зависимостей/lockfile и системных конфигураций
  блокируются серверным скриптом для отдельного ручного rollout.
- Если `main` успел измениться до начала установки, скрипт отклоняет
  устаревший SHA. Новый CI для свежего коммита выполнит отдельную попытку.
- При откате с несовпадающим checkout создаётся флаг согласования,
  запрещающий следующий деплой до вмешательства администратора.
- Первое автоматическое развёртывание этого изменения будет
  *техническим обновлением SHA*: оно не меняет бизнес-логику LMS.

## Предусловия

Нужны четыре существующих секрета (`LMS_DEPLOY_HOST`,
`LMS_DEPLOY_USER`, `LMS_DEPLOY_SSH_KEY`,
`LMS_DEPLOY_KNOWN_HOSTS`) и ранее установленный скрипт на VDS.
Если в GitHub Environment `production` включены required reviewers,
действие будет ожидать подтверждения, то есть полной автоматизации
не произойдёт. Для unattended production развёртывания защиту reviewers
нужно отключить осознанно (оставив ограничение ветки `main`).
Ручной `Deploy LMS (manual)` остаётся доступен.

## Известное ограничение

GitHub проверяет техническую корректность, но не заменяет визуальные
проверки интерфейса. Деплой может на короткое время останавливать LMS
на резервное копирование и сборку. При проблемах требуется проверка
журнала Actions и состояния сервиса; откат не равен восстановлению БД.
