## Перед обслуживанием (без изменения production)

1. Проверить зелёные GitHub Checks для PR #34 и актуального `main`, миграции / lockfile в diff.
2. `git status --short`, `git log -1 --oneline`, `git fetch origin main`, `git diff --name-status HEAD origin/main`; при локальных изменениях остановиться.
3. Подтвердить `systemctl status lms`, `curl -fsS https://lms.dvizh-school.ru/api/health`, `nginx -t`, свободный диск, права и доступность БД.
4. Назначить окно обслуживания; **не менять** соседние сайты `dvizh-school.ru` и `edu.dvizh-school.ru`.

## План окна обслуживания

1. Записать deployed SHA и время, остановить **все** экземпляры LMS/worker. Проверить, что новых записей нет.
2. Создать новую **парную** согласованную резервную копию: PostgreSQL `lms` через `pg_dump -Fc`; uploads из реального `UPLOAD_DIR`; прежний `/var/www/lms/client-dist/`. Использовать `umask 077`, `/var/backups/lms` (0700). Не печатать пароль/URI БД.
3. Проверить целостность каждого архива; желательно пробное восстановление дампа в отдельную БД без изменения `lms`. При неуспехе **не начинать обновление**.
4. `git merge --ff-only origin/main` (без reset), настроить `PATH=/opt/node24/bin:$PATH`. Запустить `npm ci`, проверки целостности и обе сборки по `DEPLOY.md`.
5. Если новая версия содержит миграции — отдельно изучить их и мигрировать **только после проверенного backup**. Для PR #34 миграций не добавлено; не выполнять их «на всякий случай» без сверки diff.
6. Проверить `APP_ORIGIN` из server/.env с уже собранным кодом, не публикуя секреты. Проверить права чтения `server/dist` и `node_modules` для пользователя `lms`.
7. Обновить frontend через `rsync -a --delete --chmod=D755,F644`, запустить `lms.service`.
8. Проверить `curl -fsS http://127.0.0.1:3001/health`, `/health/db`, публичные `/api/health` и HTTPS `/`. При ошибке остановиться и перейти к управляемому откату.

## Откат и приёмка

- **Без миграций**: при необходимости вернуть ранее записанный SHA, прежнюю клиентскую сборку и совместимую серверную сборку, перезапустить сервис; проверить health. Не использовать `git reset --hard` без проверки локальных файлов.
- **При миграциях/новых записях**: обычный откат бинарников может быть небезопасен; восстановление БД и uploads требует отдельного осознанного решения и приведёт к потере записей после backup.
- Проверки в браузере (отложены владельцем): администратор открывает курс «администратор», предпросмотр, видео, вложение и демотест; сравнивает счётчик попыток и события до/после. Проверить роли/доступы и отсутствие `attachment_download` в режиме предпросмотра.
- Cloudflare Stream в предпросмотре остаётся без встроенного плеера; поддержка отдельно.

**Автоматический full-stack деплой пока не включать**, до проверки восстановления и сценария перезапуска на VDS.
