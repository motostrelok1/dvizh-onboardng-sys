# Дополнения, замечания и безопасность LMS

Дата проверки: 4 октября 2026 года. Проверенная версия: `7385d7ac4572e65fe0b4f50354f72e374817ad80`.

Документ дополняет `PROGRESS.md` и `docs/SPEC.md`. Это backlog рекомендаций, а не изменение согласованной спецификации и не отметка о выполнении задач. Создан по отдельному запросу владельца; этап 7c и остальные задачи не выполнялись.

## Границы проверки

Проведён статический обзор исходников, конфигурации и плана. Приложение не запускалось; production, Nginx, firewall, история секретов и фактические зависимости на сервере не проверялись. «Подтверждено кодом» означает наличие конкретного условия в исходниках, а не успешную эксплуатацию в production. Уязвимости зависимостей/CVE без проверки lockfile и актуальных advisory не заявляются.

Приоритеты: P0 — закрыть до публикации сервиса; P1 — до использования реальных данных сотрудников; P2 — улучшить надёжность и сопровождение. Риски конфигурации зависят от фактического деплоя.

## Что уже сделано хорошо

- Монорепозиторий client/server, TypeScript, Fastify, миграции PostgreSQL.
- Серверные проверки роли администратора и общий `checkCourseAccess`.
- Скачивание вложений проверяет доступ к соответствующему курсу.
- В просмотренных запросах используются SQL-параметры; SQL injection не подтверждена.
- Пароли хешируются bcrypt; токены генерируются через randomBytes(32), в БД сохраняются SHA-256-хеши.
- Принятие одного приглашения защищено транзакцией и блокировкой FOR UPDATE.
- Cookie имеет HttpOnly и SameSite=Lax.
- Текст урока отображается обычным React-текстом; stored XSS через текст урока в просмотренном компоненте не подтверждён.
- Есть последовательный план и критерии завершения этапов.

## Подтверждённые проблемы и риски безопасности

### SEC-01 — Отключённый сотрудник сохраняет действующую сессию — P1

**Где:** `server/src/auth/service.ts`, getUserBySession; `server/src/routes/admin-users.ts`.

Вход проверяет is_active=true, но чтение существующей сессии проверяет только срок сессии. PATCH сотрудника меняет is_active без удаления сессий. Поэтому отключённый пользователь с действующей cookie продолжает проходить requireAuth, потенциально до истечения 30 дней.

**Исправление:** проверять is_active в каждом разрешении сессии, при отключении отзывать все сессии пользователя. Применить ту же проверку в /auth/me.

**Проверка:** после отключения сотрудника ранее выданная cookie получает 401 на уроке, скачивании и /auth/me; повторный вход запрещён.

### SEC-02 — Cookie сессии без Secure — P0 для публичного сервиса

**Где:** `server/src/routes/auth.ts`, setSessionCookie.

Флаг secure отсутствует. HttpOnly не предотвращает передачу cookie по HTTP, если такой запрос возможен. Фактическая возможность перехвата зависит от HTTPS/HSTS и инфраструктуры.

**Исправление:** Secure в production, HTTPS, корректный доверенный proxy, HSTS после проверки HTTPS. Рассмотреть имя __Host- для production-cookie (Secure, Path=/, без Domain). Согласовать атрибуты установки и очистки cookie.

**Проверка:** production Set-Cookie содержит Secure, HttpOnly, SameSite и корректный срок; приложение доступно через HTTPS, HTTP перенаправляется.

### SEC-03 — Публикация PostgreSQL с известным паролем — P0 при внешней доступности

**Где:** `docker-compose.yml`.

Указаны POSTGRES_PASSWORD=lms и ports: "5432:5432". Compose публикует порт на интерфейсах хоста; реальная доступность снаружи зависит от firewall. Использование этой конфигурации на публичном VDS создаёт риск прямого доступа к БД.

**Исправление:** отдельная production-конфигурация, уникальный секрет из окружения, отсутствие внешней публикации БД. Для локальной разработки при необходимости привязать порт к 127.0.0.1. Отдельные права runtime и миграций; смена пароля уже созданной БД требует действий в самой БД, одного изменения env недостаточно.

**Проверка:** БД недоступна из внешней сети; runtime-пользователь не имеет административных прав; секретов нет в git.

### SEC-04 — Небезопасное построение пути загруженного файла — P1

**Где:** `server/src/storage.ts`; `server/src/routes/admin-attachments.ts`.

storedFileName добавляет UUID, но оставляет оригинальное имя целиком; attachmentPath использует join без проверки границ каталога. Имя из multipart может содержать разделители и сегменты пути. Префикс UUID сам по себе не гарантирует containment после нормализации пути. lessonId также используется в пути до проверки UUID/существования урока.

Доступ к загрузке ограничен администратором. Это потенциальный path traversal/запись вне uploads; эксплуатация через конкретный multipart-парсер и ОС не проверялась.

**Исправление:** хранить файл как UUID + разрешённое расширение, исходное имя оставлять только в метаданных; проверять UUID и существование урока до записи; проверять resolve/relative для границ uploads; исключить переходы через symlink, ограничить права процесса.

**Проверка:** имена с ../, обратными слешами и абсолютными путями не влияют на путь хранения; неизвестный lessonId не создаёт каталог или файл; запись за пределами uploads невозможна.

### SEC-05 — Проверяется расширение, а не содержимое файла — P1

**Где:** `server/src/routes/admin-attachments.ts`.

Список расширений и лимит 50 МБ есть, проверки сигнатуры/структуры файла нет. Переименование вредоносного файла не делает его PDF или изображением. Даже корректные документы могут содержать опасное содержимое.

**Исправление:** проверять сигнатуру и структуру формата, использовать MIME как дополнительный сигнал; определить политику макросов и антивирусного сканирования/карантина. Хранить uploads вне публичного web-root, отдавать только через проверяемый endpoint; добавить Content-Type, nosniff и безопасный Content-Disposition.

**Проверка:** файл с разрешённым расширением и неверным содержимым отклоняется; прямой публичный URL к uploads не работает. Content-Disposition уже установлен — сохранить это поведение.

### SEC-06 — Нет прикладного ограничения частоты входа — P1

**Где:** `server/src/routes/auth.ts`, `server/src/index.ts`.

В просмотренном приложении нет rate limiting входа/принятия приглашений. Возможны перебор паролей и нагрузка bcrypt. Внешний лимит Nginx не проверен.

**Исправление:** лимиты по IP и учётной записи, задержка при повторных ошибках, мониторинг; осторожно с постоянной блокировкой, которую можно использовать против владельца аккаунта. Ограничить типы/длину email, токена и пароля.

**Проверка:** серия неудачных запросов приводит к 429 или контролируемой задержке; разные IP не обходят лимит на аккаунт; успешный вход работает.

### SEC-07 — Токен приглашения находится в URL — P1

**Где:** `server/src/routes/auth.ts`; `server/src/index.ts` (logger: true).

Токен передаётся в пути запроса. Такие URL могут попадать в стандартные логи приложения/прокси, историю браузера и инструменты наблюдения. Фактические production-логи не проверялись.

**Исправление:** маскировать сегмент токена в URL в логах приложения и Nginx, исключить cookie/пароли/токены из telemetry; Cache-Control: no-store и Referrer-Policy: no-referrer на приглашениях и чувствительных ответах. Ограничить срок доступа к логам.

**Проверка:** после принятия приглашения сырого токена нет в логах приложения/прокси; приватные ответы не кешируются публично.

### SEC-08 — Повторные приглашения меняют пароль без отзыва старого доступа — P1

**Где:** `server/src/auth/service.ts`, createInvitation/acceptInvitation.

Можно выпустить несколько приглашений. Принятие одного помечает использованным только его, меняет пароль и активирует пользователя; остальные приглашения и старые сессии сохраняются. Отдельные действующие ссылки могут повторно менять пароль. Приглашение также может вернуть is_active=true отключённому сотруднику.

**Исправление:** определить, является ли повторное приглашение восстановлением доступа. При новом приглашении отзывать предыдущие по принятой политике; при установке/смене пароля отзывать старые сессии и остальные ссылки. Проверять допустимость активации. Конкурентные приглашения одного пользователя синхронизировать блокировкой пользователя, не только отдельной ссылки.

**Проверка:** после принятия одной ссылки остальные недействительны, старые сессии отозваны; конкурентные запросы дают один согласованный результат.

### SEC-09 — Дедлайн проверяется только по сохранённому статусу — P1

**Где:** `server/src/access.ts`; `server/src/jobs/deadlines.ts`.

checkCourseAccess блокирует status=overdue, но не сравнивает deadline с текущим временем. Job запускается раз в 60 секунд; после срока остаётся окно доступа, при сбое job — дольше.

**Исправление:** проверять deadline непосредственно при доступе к курсу, уроку, вложению и будущей попытке теста. Job использовать для фиксации статуса и уведомлений. Отдельно определить правила доступа к завершённым курсам.

**Проверка:** сразу после дедлайна запрос запрещён даже при выключенном job; перенос срока возвращает доступ.

### SEC-10 — Диагностический endpoint раскрывает имена таблиц — P2

**Где:** `server/src/index.ts`, /health/tables.

Endpoint доступен без авторизации. Это раскрытие внутренней структуры, само по себе не доступ к данным.

**Исправление:** удалить в production или ограничить администратором/внутренней сетью. Публичный health должен выдавать минимальную информацию.

**Проверка:** внешний неавторизованный запрос не получает список таблиц.

### SEC-11 — Недостаточная runtime-валидация API — P1

**Где:** `server/src/routes/auth.ts`, `admin-users.ts`, `admin-tests.ts`, `admin-attachments.ts`.

Типы TypeScript не проверяют реальный HTTP-ввод. Например, login читает req.body.email/password без схемы; настройки теста не проверяют диапазоны и целочисленность. Неверные UUID/типы могут приводить к исключениям и несогласованным данным.

**Исправление:** Fastify JSON Schema для params/body/query и явные response DTO; диапазоны passScore по SPEC, положительные целые maxAttempts или согласованный null; длины строк, boolean, enum, timezone. Единый обработчик ошибок без SQL, stack trace и внутренних путей в ответах.

**Проверка:** неправильные типы, UUID, диапазоны, пустые и слишком длинные значения дают стабильный 400; нормальные запросы сохраняют поведение.

## Требуют дополнительной проверки

Эти пункты не являются подтверждёнными уязвимостями.

- **CSRF — P1:** SameSite=Lax уже снижает риск. Проверить модель same-site поддоменов, Origin/Referer, типы входных данных и все изменяющие endpoint. При необходимости добавить CSRF-токены; CORS сам по себе не заменяет CSRF-защиту.
- **Черновики курсов — P1:** checkCourseAccess разрешает назначенный курс, если он не archived; published не требуется. Если по SPEC черновик недоступен сотрудникам, добавить проверку статуса. Сначала согласовать ожидаемое поведение.
- **Защита видео — P1:** self_hosted возвращает videoRef клиенту. Если видео публично доступно по постоянной ссылке, закрытие LMS не отзывает прямой доступ. Проверить хранилище и CDN; использовать авторизованный endpoint или короткоживущие подписанные ссылки.
- **URL видео и браузерные политики — P2:** разрешить согласованные HTTPS-хосты/форматы, настроить CSP frame-src/media-src и Referrer-Policy. Серверной загрузки произвольного videoRef в просмотренном коде нет: SSRF не подтверждён.
- **Зависимости — P1:** проверить package-lock.json через актуальные advisory/npm audit, добавить автоматические обновления и проверку поддержки Node/Fastify/Vite. Не утверждать наличие CVE по одному номеру версии.
- **Секреты и персональные данные — P1:** проверить git history, а не только текущие файлы; secret scanning, запрет .env/ключей/дампов/реальных данных. Public-репозиторий сам по себе не уязвимость. При утечке сначала отозвать секрет.
- **Production — P1:** HTTPS, firewall, закрытая БД, отсутствие публичного Vite dev server, права процесса, trusted proxy, резервные копии и проверка восстановления.
- **Приватность — P1:** доступ к аналитике по ролям, сроки хранения событий/отчётов, удаление/экспорт данных, отсутствие паролей и ответов теста в ненужных логах. Применимые требования определить отдельно под реальное использование.

## Функциональные и технические предложения

### DEV-01 — Завершить этап 7c по SPEC

Серверные попытки теста, проверка ответов только на сервере, maxAttempts, passScore, сохранение результата, разбор только при showCorrectAnswers=true.

До старта попытки и отправки ответов проверять пользователя, курс, дедлайн и принадлежность вопроса/варианта попытке. Не отдавать is_correct сотруднику до разрешённого разбора. Лимит попыток защищать транзакцией от параллельных стартов; повторная отправка завершённой попытки не должна менять балл. Определить версионирование теста при редактировании и правила частичного балла по SPEC.

### DEV-02 — Реальные автоматические тесты и CI — P1

В server/package.json test указывает на dist_test_placeholder; полноценного набора тестов в просмотренном дереве нет. Curl-проверки полезны, но не предотвращают регрессии.

Добавить Fastify inject и отдельную PostgreSQL для integration-тестов: 401/403, роли, отключение сотрудника, приглашения, дедлайны, скачивание, попытки теста и конкурентные запросы. Проверять изоляцию данных и миграции.

CI: npm ci → server build → реальные tests → client build. Дополнительно аудит зависимостей. Не подменять отсутствующие тесты успешной заглушкой.

### DEV-03 — Очистить сгенерированные JS в client/src — P2

В src есть пары .js/.tsx и .js/.ts не только App/main. client/tsconfig.json не задаёт noEmit/outDir, а build запускает tsc -b. Вероятно, JS — результат компиляции рядом с исходниками, а не отдельная первоначальная версия.

Сначала проверить разрешение импортов Vite, затем настроить typecheck без записи в src, удалить подтверждённые generated-файлы и tsbuildinfo, добавить правила gitignore. Критерий: чистая сборка не создаёт JS в src и использует актуальный TypeScript.

### DEV-04 — Привести документацию в соответствие — P2

- В PROGRESS.md пока указать React + Vite; PWA обозначить запланированной до этапа 12.
- Заменить заглушку «Как запустить» рабочими командами.
- README содержит старые вводные про экран статуса/отсутствие админки/контента — обновить под текущую версию.
- Разделить development и production: env, установка через npm ci, миграции, запуск, Nginx, uploads, резервные копии и rollback.
- Сохранить один основной план; additions.md использовать как backlog с приоритетами и статусами.

### DEV-05 — Надёжность загрузок — P1

Файл записывается до проверки связи с уроком в БД; при ошибке INSERT или pipeline нет общего cleanup. Это создаёт сиротские/частичные файлы и риск заполнения диска.

Проверять урок до загрузки; писать во временный файл, удалять при любой ошибке, публиковать после успешного завершения; предусмотреть согласование файловой системы и БД. Ввести квоты по месту/пользователю, лимиты параллельности, мониторинг свободного места и уборку сирот. Проверить удаление файлов при каскадном удалении урока/курса.

### DEV-06 — Семантика PATCH — P2

- admin-users.ts: coalesce(departmentId, department_id) не позволяет очистить отдел через null.
- admin-tests.ts: отсутствие maxAttempts в PATCH превращается в null, сбрасывая ранее заданный лимит.

Различать «поле отсутствует» и «явно null»; покрыть обновление одного поля проверкой сохранности остальных.

### DEV-07 — Планировщик и конкуренция — P2

Job дедлайнов работает внутри каждого процесса, setInterval допускает перекрытие медленных запусков. Текущий UPDATE с условием статуса во многом идемпотентен: нельзя утверждать, что сейчас автоматически дублируются уведомления, которых ещё нет.

Перед этапом 11 выбрать worker/advisory lock/очередь, добавить идемпотентные ключи уведомлений, retry/backoff, мониторинг и graceful shutdown таймера/БД. Уведомление должно доставляться один раз даже при рестарте и нескольких backend.

### DEV-08 — Дедлайны и часовые пояса — P2

Сейчас хранится переданный момент времени; PROGRESS отмечает отсутствие пересчёта конца дня сотрудника. Определить semantics даты и времени, использовать UTC в хранении и IANA timezone в интерфейсе. Проверить границы суток и DST, не менять правило неявно.

### DEV-09 — Целостность данных — P2

Для tests(scope,parent_id), порядка модулей/уроков/вопросов и массовых назначений проверить ограничения БД и транзакции. SELECT перед INSERT и max(position)+1 подвержены гонкам; уникальность должна обеспечиваться БД, а 409 обрабатываться приложением. Проверить существование родителя полиморфного теста и удаление связанных данных.

### DEV-10 — Продолжить основной план

После 7c: журнал событий (8), карточка сотрудника/дашборд (9), ежедневные отчёты и аналитика (10), уведомления (11), PWA/деплой (12).

Для событий: server-derived userId, проверка доступа к объекту, ограничения пакета и частоты, eventId для дедупликации, различать время клиента/сервера. Клиентское событие не должно само подтверждать успешное прохождение теста.

Для PWA: кешировать оболочку; приватные API, ответы тестов, приглашения и файлы не включать в общий precache. Согласовать offline-режим, очистку данных при выходе и дедлайн при повторном подключении.

### DEV-11 — Удобство интерфейса — P2

После функционального ядра: мобильные экраны, единые loading/error/empty states, понятные статусы и дедлайны, подтверждение удаления, доступность с клавиатуры, подписи полей, фокус после ошибок. Прогресс показывать по согласованной серверной модели, а не по одному открытию страницы.

2. До реальных сотрудников: SEC-01, SEC-04–09, SEC-11; реальные security regression tests.
3. Этап 7c с безопасной серверной моделью попыток.
4. Отдельный hardening-этап: CI, cleanup client/src, ошибки/валидация, файлы, документация, аудит зависимостей.
5. Этапы 8–12 с защитой событий, аналитики, уведомлений и PWA.
6. Перед production: staging-проверка ролей/доступа, восстановления backup, сетевых ограничений и нагрузочных лимитов.

Не отмечать задачи выполненными по факту добавления этого документа. Для каждого исправления записывать отдельный commit, проверку и результат.
